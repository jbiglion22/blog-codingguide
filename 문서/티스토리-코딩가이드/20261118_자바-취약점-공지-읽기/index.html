작성일 2026.11.18 · 자바 · 예제는 OpenJDK 25.0.4(JetBrains 배포판)로 실행

[[ 이미지: 타이틀 - 자바 취약점 공지 읽는 법 (01-타이틀.png) ]]

2026년 11월 18일, 한국인터넷진흥원(KISA) 보호나라에 「Oracle 제품 보안 업데이트 권고」가 올라왔고, 과학기술정보통신부는 자바 실행 환경 취약점에 대해 긴급 점검을 권고했습니다. 발견한 보안업체가 '자바포셸(Java4Shell)'이라 이름 붙인 취약점입니다.

그런데 공지를 열면 CVE-2026-114938, CVSS 8.1, 17.0.21.0.3 같은 번호가 줄줄이 나옵니다. 이 공지를 한 줄씩 읽으며 취약점이 무엇인지, 숫자가 무슨 뜻인지, 내 자바가 해당되는지 확인하는 법을 정리하겠습니다. 공격 방법은 다루지 않습니다.

 

1. 취약점은 버그와 무엇이 다를까

버그는 프로그램이 의도와 다르게 동작하는 오류이고, 그중 다른 사람이 악용해 피해를 줄 수 있는 오류를 취약점이라고 부릅니다. 이번 자바 취약점은 두 낱말로 설명됩니다.

  • 메모리 손상: 들어온 데이터를 담을 메모리 칸을 넘어 옆 칸까지 덮어쓰면, 프로그램이 원래 하지 않을 동작을 할 수 있습니다. KISA 공지는 이를 '힙 기반 버퍼 오버플로(Heap-based Buffer Overflow)'라고 적었습니다.
  • 원격 코드 실행(RCE): 공격자가 네트워크로 데이터를 보내 그 컴퓨터에서 원하는 코드를 실행하게 만드는 것입니다.

문제가 생긴 곳은 Base64 디코더입니다. Base64는 그림이나 파일 같은 데이터를 글자로 바꿔 주고받는 방식이고, 디코더는 그 글자를 원래 데이터로 되돌리는 부분입니다.

그런데 오라클과 오픈JDK 공지는 취약한 구성 요소를 'Compiler(hotspot/compiler)'로 분류했습니다. 여기서 컴파일러는 우리가 소스 코드를 javac로 컴파일하는 그 컴파일러가 아닙니다. 실행 중에 자주 쓰이는 코드를 CPU에 맞는 빠른 기계어로 바꿔 주는 HotSpot의 JIT 컴파일러입니다. JIT 컴파일러는 Base64 디코딩을 CPU 전용 명령으로 짠 고속 코드로 바꿔 끼우는데, 취약점은 이 Base64 디코더 최적화 코드에 있었습니다. 그래서 '구성 요소는 컴파일러, 실제 문제는 Base64 디코딩'이라는 두 설명이 함께 나옵니다. 애플리케이션 코드나 javac의 오류가 아닙니다.

모든 자바가 똑같이 위험한 것은 아니다

발견 업체 설명으로는 이 고속 코드가 x86-64 CPU의 AVX-512 VBMI 명령어를 쓰기 때문에, 이 명령어를 지원하는 CPU(인텔 제온 Ice Lake 이후 일부, AMD Zen 4 이후 등)에서만 문제 경로가 실행됩니다. ARM64 CPU는 영향을 받지 않고, 이 명령어가 없는 x86-64 CPU도 알려진 영향 대상이 아닙니다.

즉 원격 코드 실행까지 가려면 영향받는 자바 버전, 해당 CPU, 바깥에서 받은 Base64 데이터를 이 경로로 처리하는 프로그램이라는 조건이 겹쳐야 합니다. 자바를 쓰는 모든 프로그램이 원격 코드 실행에 노출되는 것은 아닙니다. 그래도 조건을 일일이 따지기보다 업데이트하는 것이 기본입니다.

2. 보안 공지를 한 줄씩 읽어 보기

CVE 번호: 취약점의 주민등록번호

CVE-2026-114938에서 CVE는 'Common Vulnerabilities and Exposures'의 줄임말입니다. 전 세계가 같은 취약점을 같은 이름으로 부르기 위한 번호로, 미국 비영리기관 MITRE가 운영하는 CVE 프로그램에서 관리합니다. 2026은 배정된 해, 뒤는 일련번호입니다. 별명이 달라도 CVE 번호가 같으면 같은 취약점입니다.

CVSS 점수: 8.1점과 9.2점은 왜 다를까

CVSS(Common Vulnerability Scoring System)는 취약점의 위험도를 0~10점으로 매기는 국제 기준입니다. 이번 취약점에는 점수가 두 개 나왔습니다.

  • 8.1점: 오라클이 CVSS 3.1 기준으로 매긴 점수
  • 9.2점: 발견 업체가 CVSS 4.0 기준으로 매긴 점수

CVSS는 버전마다 계산 방식이 달라 같은 취약점도 점수가 다를 수 있으니, 숫자와 함께 어느 버전 기준인지를 봐야 합니다.

점수 뒤에 숨은 항목들

점수보다 쓸모 있는 것은 점수를 만든 항목입니다. 오라클 공지의 항목을 풀면 이렇습니다.

  • 공격 경로(Attack Vector): 네트워크 → 원격에서 공격할 수 있습니다.
  • 공격 복잡도(Attack Complexity): 높음 → 공격에 성공하려면 맞춰야 할 조건이 까다롭습니다.
  • 필요 권한(Privileges Required): 없음 → 로그인 같은 계정이 없어도 됩니다.
  • 사용자 동작(User Interaction): 필요 없음 → 누군가 링크를 누르지 않아도 됩니다.
  • 범위(Scope): 변경 없음(Unchanged) → 피해가 취약한 구성 요소와 같은 보안 범위 안에서 일어난다는 뜻입니다. 다른 범위의 권한까지 넘어가면 '변경됨(Changed)'이 되고 점수가 올라갑니다.
  • 기밀성·무결성·가용성 영향: 모두 높음 → 성공하면 정보 유출, 데이터 변조, 서비스 중단이 모두 가능합니다.

정리하면 "조건을 맞추기는 어렵지만, 맞추면 계정 없이 원격에서 큰 피해를 줄 수 있다"는 뜻입니다. 오라클은 웹 서비스처럼 바깥 데이터를 이 기능에 넘기는 경로로 악용될 수 있다고 설명했고, 정부도 인터넷에 열린 시스템부터 점검하라고 했습니다. 다만 이 점수에는 앞에서 본 CPU 조건이 담겨 있지 않습니다.

영향 버전과 수정 버전

공지 표의 '영향받는 버전'은 취약점이 있는 버전, '해결 버전'은 고친 버전입니다. 예를 들어 KISA 공지에서 자바 17은 영향 버전이 17.0.21.0.3, 해결 버전이 17.0.21.1로 적혀 있습니다.

여기서 주의할 점은 공지에 실린 취약점마다 해당되는 버전이 다르다는 것입니다. 공지에는 취약점 여러 개가 함께 실렸는데, 자바포셸(CVE-2026-114938)만 보면 오라클 자바 SE와 오픈JDK 모두 17·21·25·27 버전이 해당됩니다. 자바 11은 영향 목록에 없고, 자바 8은 일반 빌드가 아닌 성능용 빌드 8u511b33-perf만 들어 있습니다. 표에 8·11의 수정 버전이 보이는 것은 같은 공지의 다른 취약점 때문이고, 8 성능 빌드를 쓴다면 일반 빌드(8u513)와 구분해 오라클 안내에서 수정 버전을 따로 확인해야 합니다. 또 이 표는 오라클 자바 SE 기준이라, 다른 회사가 배포한 자바는 번호가 다를 수 있습니다.

 

3. 자바 버전 번호는 이렇게 읽는다

  • 자바 8: '8u513'처럼 씁니다. 8은 큰 버전, u 뒤는 업데이트 번호이고, 1.8.0_513으로도 표시됩니다.
  • 자바 10 이후: '17.0.21'처럼 기능(주) 버전, 중간 버전, 업데이트 번호 순서입니다. 급한 보안 수정은 17.0.21.1처럼 네 번째 숫자가 붙기도 합니다.

자바는 6개월마다 새 버전을 내고, 그중 일부만 오래 보안 업데이트를 해 주는 LTS(장기 지원)로 정합니다. 8, 11, 17, 21, 25가 LTS이고, 회사 시스템이 주로 이 버전을 쓰기 때문에 보안 공지에도 자주 나옵니다.

오라클 자바와 오픈JDK 배포판

자바의 소스 코드는 오픈JDK라는 이름으로 공개돼 있고, 여러 회사가 이 소스로 각자 자바를 배포합니다. 오라클 자바 SE, 이클립스 테뮤린, 아마존 코레토, 아줄 줄루, 마이크로소프트 빌드 등이 있고, 안드로이드 스튜디오 같은 개발 도구는 젯브레인스(JetBrains)가 만든 자바를 안에 넣어 둡니다.

뿌리가 같아 같은 취약점의 영향을 받지만, 고친 버전을 내는 시점과 번호는 배포한 곳마다 다릅니다. KISA도 오픈JDK 기반 배포판은 배포판별 수정 버전을 적용하라고 안내했습니다. 그래서 '내 자바가 고쳐졌는지'는 내 자바를 배포한 곳의 보안 공지에서 CVE-2026-114938이 고쳐진 버전을 확인하는 것이 가장 정확합니다.

 

4. 내 자바 버전 확인하기

가장 간단한 방법은 명령 프롬프트(또는 터미널)에서 다음을 입력하는 것입니다.

java -version

제 컴퓨터에서는 이렇게 나왔습니다.

'java'은(는) 내부 또는 외부 명령, 실행할 수 있는 프로그램, 또는
배치 파일이 아닙니다.

정확히는 '명령어로 바로 부를 수 있는 자바가 없다'는 뜻입니다. 프로그램이 자기 폴더 안에 넣어 둔 자바는 이 명령으로 보이지 않습니다. 실제로 안드로이드 스튜디오 폴더 안에는 자바가 있었습니다.

이번에는 자바 코드로 실행 중인 자바의 정보를 출력해 보겠습니다. 자바 11부터는 소스 파일 하나를 java 파일이름.java로 바로 실행할 수 있습니다.

public class JavaVersion {
    public static void main(String[] args) {
        Runtime.Version v = Runtime.version();
        System.out.println("전체 버전   : " + v);
        System.out.println("기능(주) 버전: " + v.feature());
        System.out.println("업데이트 번호: " + v.update());
        System.out.println("배포한 곳   : " + System.getProperty("java.vendor"));
        System.out.println("설치 위치   : " + System.getProperty("java.home"));
    }
}

안드로이드 스튜디오에 들어 있는 자바로 실행한 결과입니다.

전체 버전   : 25.0.4+-16339643-b508.27
기능(주) 버전: 25
업데이트 번호: 4
배포한 곳   : JetBrains s.r.o.
설치 위치   : C:\Program Files\Android\Android Studio\jbr

코드에서 Runtime.version()은 실행 중인 자바의 버전 정보를 돌려주고, feature()와 update()는 그중 기능 버전과 업데이트 번호만 꺼냅니다. java.vendor는 배포한 회사, java.home은 설치 위치입니다. 이 자바는 젯브레인스가 배포한 25 버전의 4번째 업데이트라, 오라클 표의 25.0.5.1과 숫자를 바로 비교할 수 없습니다.

안드로이드 스튜디오에 들어 있는 자바는 젯브레인스 런타임(JBR)입니다. 보통 스튜디오를 업데이트할 때 새 JBR이 함께 들어오지만, JBR 버전은 스튜디오 버전과 따로 움직일 수 있습니다. 그래서 업데이트 뒤 위 코드로 실제 JBR 버전을 출력해 보고, 젯브레인스 런타임 배포처 안내에서 그 버전에 보안 수정이 들어갔는지 확인하는 것이 정확합니다.

5. 2021년 Log4Shell과 무엇이 다를까

'자바포셸'은 2021년 12월의 'Log4Shell'을 떠올리게 합니다. 둘 다 자바와 관련된 원격 코드 실행 취약점이지만, 문제가 생긴 위치가 다릅니다.

  • Log4Shell: 기록(로그)을 남기는 라이브러리 Log4j의 취약점이라, 프로그램마다 Log4j를 바꿔 다시 배포해야 했습니다.
  • 자바포셸: 프로그램이 돌아가는 실행 환경(JDK) 자체의 취약점이라, 프로그램을 돌리는 자바를 업데이트하는 것이 기본 대응입니다.

6. 공지를 읽은 다음 개발자·운영자가 할 일

정부·KISA 안내에 발견 업체 권고를 더해 정리하면 이렇습니다.

  1. 어떤 자바가 어떤 버전으로 어디에 깔려 있는지 확인합니다(프로그램 속 자바 포함).
  2. 그 자바를 배포한 곳의 보안 공지에서 CVE-2026-114938 수정 버전을 확인합니다.
  3. 인터넷에 열린 서비스, 그룹웨어, ERP처럼 바깥 데이터를 받는 시스템부터 업데이트합니다. 바로 업데이트하기 어렵다면 발견 업체가 안내한 임시 방법(x86-64에서 Base64 고속 경로를 끄는 JVM 옵션, ARM에서는 쓰지 말 것)을 검토합니다.
  4. 업데이트한 뒤 서비스를 다시 시작합니다. 재시작 전에는 예전 자바를 계속 쓸 수 있습니다.
  5. 위 코드처럼 실행 중인 자바 버전을 출력해 운영 환경 반영을 확인합니다.

다음 보안 공지를 열었을 때 볼 다섯 칸

보안 공지는 번호가 많아 어려워 보이지만 볼 곳은 정해져 있습니다. CVE 번호로 어떤 취약점인지, CVSS 점수와 기준 버전으로 얼마나 위험한지, 공격 경로·필요 권한 같은 항목으로 어떤 상황에서 위험한지 읽습니다. 그리고 영향 버전과 수정 버전을 내 자바의 버전·배포한 곳과 맞춰 보고, CPU 같은 조건이 붙어 있는지 확인합니다. 이 다섯 칸을 읽으면 다음 공지도 스스로 판단할 수 있습니다.

이 글은 2026년 11월 18일 한국인터넷진흥원 보호나라 보안공지와 오라클 보안 공지를 바탕으로 정리했습니다. 영향 버전과 수정 버전은 공지 수정에 따라 바뀔 수 있으니, 업데이트 전 배포처의 공식 안내를 함께 확인해 주세요.
