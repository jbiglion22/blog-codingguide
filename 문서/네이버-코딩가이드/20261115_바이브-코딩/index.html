[[ 이미지: 타이틀 - 바이브 코딩이 뭐길래 (01-타이틀.png) ]]

요즘 개발 관련 글을 보면 '바이브 코딩'이라는 말이 자주 나옵니다. 처음 들었을 때는 음악을 틀어 놓고 코딩한다는 뜻인가 싶었습니다.

찾아보니 AI에게 말로 설명해서 코드를 짜게 하는 방식을 말한다고 합니다. 마침 저도 요즘 코딩할 때 AI 코딩 도구를 쓰고 있어서, 바이브 코딩이 무엇인지와 직접 써 보며 느낀 점을 정리해 봤습니다.

 

바이브 코딩은 어디서 나온 말일까

이 말은 2025년 2월, 안드레이 카파시라는 AI 연구자가 X(옛 트위터)에 처음 쓴 표현이라고 합니다. 테슬라에서 AI 개발을 이끌었고 오픈AI를 함께 세운 사람으로 알려져 있습니다.

그가 말한 바이브 코딩은 코드를 한 줄씩 직접 쓰는 대신, AI에게 원하는 것을 말하고 결과를 보면서 '느낌(vibe)대로' 프로그램을 만들어 가는 방식이었습니다. 코드가 있다는 것조차 잊을 정도로 AI에게 맡긴다는 뜻이었다고 합니다.

이 말은 1년도 안 돼 널리 퍼졌습니다. 영국의 콜린스 사전은 2025년 11월에 '바이브 코딩'을 그해의 단어로 뽑았습니다. 처음 등장한 뒤로 쓰임이 크게 늘었다는 것이 이유였다고 합니다.

 

예전 코딩과 뭐가 다를까

가장 큰 차이는 코드를 누가 쓰느냐입니다.

[[ 이미지: 예전 코딩과 바이브 코딩 비교 (02-예전코딩-바이브코딩.png) ]]

예전에는 사람이 문법을 알고 코드를 직접 써야 했습니다. 바이브 코딩에서는 "폴더 안의 엑셀 파일을 하나로 합쳐 줘"처럼 하고 싶은 일을 말로 설명하면 AI가 코드를 씁니다. 사람은 결과를 보고, 마음에 들지 않으면 다시 말로 고쳐 달라고 합니다.

코드를 쓰는 일이 줄어든 대신, 무엇을 원하는지 정확히 설명하는 일과 결과가 맞는지 확인하는 일이 더 중요해졌다고 볼 수 있습니다.

 

직접 써 봤다

저는 요즘 코딩할 때 AI 코딩 도구(Claude Code)를 쓰고 있습니다. 컴퓨터의 작업 폴더에서 AI와 대화하면서 코드를 만들고, 실행해서 결과까지 확인하는 방식입니다.

[[ 이미지: 말로 설명하면 AI가 코드를 쓰는 만화 (03-말로-코딩-만화.png) ]]

 

엑셀 파일 합치기

처음 맡겨 본 일은 여러 엑셀 파일을 하나로 합치는 파이썬 코드였습니다. 원하는 것을 설명하자 AI가 코드를 짰고, 예제 엑셀 파일 3개를 직접 만들어 코드를 돌려 본 뒤 "3개 파일, 12행이 합쳐졌다"고 결과까지 알려 줬습니다.

[[ 이미지: 엑셀 합치기를 맡긴 대화 (04-실제-대화.png) ]]

표나 그래프를 그리는 코드도 같은 방식으로 맡겼습니다. 데이터를 주고 "막대그래프로 그려 줘"라고 하면, AI가 그래프를 그리는 코드를 짜서 이미지 파일로 저장해 줍니다. 이 글에 들어간 비교 도식과 표도 그렇게 만들었습니다.

 

AI도 틀린다

편하기만 했던 것은 아닙니다. 어떤 웹 서비스에 특정 기능이 있는지 물었더니 AI가 "있다"고 자신 있게 답했는데, 실제 화면에는 그런 기능이 없었습니다. 그럴듯하게 말해서 그대로 믿을 뻔했습니다.

코드로 그림을 그리게 했을 때도 차이가 있었습니다. 표나 그래프는 잘 만들었지만, 사람이나 장면을 그린 그림은 어색해서 결국 이미지 생성 AI로 다시 만들었습니다. 잘하는 일과 못하는 일이 꽤 분명하게 나뉘었습니다.

그래도 가장 편했던 점은 코드를 처음부터 쓰지 않아도 된다는 것이었습니다. 문법을 찾아보는 시간이 줄어든 만큼, 무엇을 만들지 설명하고 결과가 맞는지 확인하는 데 더 집중할 수 있었습니다.

 

좋은 점과 조심할 점

써 보면서, 그리고 찾아보면서 정리한 내용입니다.

[[ 이미지: 바이브 코딩의 좋은 점과 조심할 점 (05-장단점.png) ]]

좋은 점은 분명합니다. 코드를 잘 몰라도 원하는 것을 만들어 볼 수 있고, 반복되는 작업을 빠르게 끝낼 수 있습니다.

조심할 점은 AI가 틀린 내용을 아주 그럴듯하게 내놓는다는 것입니다. 그리고 내가 쓰지 않은 코드라서, 문제가 생기면 어디가 잘못됐는지 찾기가 어렵습니다.

 

보안은 따로 확인해야 한다

특히 보안 문제가 자주 지적됩니다. 보안 회사 베라코드(Veracode)가 2025년에 AI 모델 100여 개에게 보안이 중요한 코딩 과제를 시켜 본 조사에서, AI가 만든 코드의 45%에서 보안 허점이 나왔다고 합니다.

[[ 이미지: AI가 만든 코드의 보안 허점 45% (06-보안-45퍼센트.png) ]]

코드가 잘 돌아간다고 해서 안전한 것은 아니라는 뜻입니다. 엑셀 정리처럼 내 컴퓨터 안에서 끝나는 일은 부담이 적지만, 로그인이나 결제, 개인정보를 다루는 프로그램이라면 전문가의 확인이 꼭 필요해 보입니다.

 

이렇게 써 보니 좋았다

[[ 이미지: 바이브 코딩 잘 쓰는 법 체크리스트 (07-잘-쓰는-법.png) ]]

  • 구체적으로 말하기 : "정리해 줘"보다 "3개 파일을 합쳐서 엑셀로 저장해 줘"처럼 결과물을 분명하게 말하면 한 번에 원하는 결과가 나올 때가 많았습니다.
  • 하나씩 시키기 : 큰 일을 한꺼번에 맡기기보다 단계별로 나눠서 시키는 편이 고치기 쉬웠습니다.
  • 결과 확인하기 : 가장 중요했습니다. 실행 결과의 숫자가 맞는지, 설명이 사실인지 직접 확인했습니다.
  • 물어보기 : 모르는 코드는 "이 줄은 무슨 뜻이야?"라고 물으면 설명해 줍니다. 그러다 보면 코드도 조금씩 읽히게 됩니다.

 

모든 코딩이 바이브 코딩으로 바뀔까

써 보면서 가장 궁금했던 것이 이 부분입니다. 앞으로는 코딩을 전부 말로 하게 될까요?

제 결론은 "아직은 아니다"입니다. 엑셀 파일을 합치거나 그래프를 그리는 것처럼 간단한 일은 바이브 코딩만으로 충분했습니다. 원하는 것을 말하고, 결과를 확인하고, 한두 번 고쳐 달라고 하면 끝났습니다.

그런데 일이 조금만 복잡해져도 사정이 달라졌습니다. 기능이 여러 개 얽히면, 하나를 고쳐 달라고 했을 때 다른 곳이 망가지는 일이 생깁니다. 어디가 문제인지 AI에게 다시 설명하다 보면, 결국 코드를 직접 들여다봐야 할 때가 많았습니다.

[[ 이미지: 난이도별로 본 바이브 코딩 (08-난이도별-바이브코딩.png) ]]

찾아보니 이 말을 처음 만든 카파시도 비슷하게 말했다고 합니다. 처음 바이브 코딩을 소개한 글에서 "주말에 한 번 만들고 버릴 프로젝트에는 나쁘지 않다"고 했고, 나중에는 자신이 정말 신경 쓰는 코드에는 바이브 코딩만으로는 부족하다는 취지로 이야기했다고 합니다.

복잡한 프로그램이 어려운 이유를 정리해 보면 이렇습니다.

  • 전체 그림이 필요하다 : 여러 기능이 어떻게 맞물려야 하는지는 만드는 사람이 정해야 합니다. 이 설계가 없으면 AI도 엉뚱한 방향으로 코드를 늘려 갑니다.
  • 작은 실수가 쌓인다 : 간단한 프로그램에서는 금방 보이는 실수도, 코드가 길어지면 숨어 있다가 나중에 문제가 됩니다.
  • 오래 고쳐 가며 써야 한다 : 한 번 쓰고 마는 코드가 아니라면, 나중에 고칠 사람이 코드를 이해할 수 있어야 합니다.
  • 책임이 따른다 : 다른 사람이 쓰는 서비스라면 오류나 보안 문제가 그대로 사용자에게 피해가 됩니다.

그래서 지금은 "코딩이 사라진다"기보다 "코딩하는 방식이 바뀌고 있다"에 가깝다고 느꼈습니다. 간단한 일은 AI에게 맡기고, 복잡한 일은 사람이 설계하고 AI를 도구로 쓰는 식입니다. AI가 빠르게 좋아지고 있으니 바이브 코딩으로 할 수 있는 범위도 점점 넓어지겠지만, 결과를 판단하는 일은 당분간 사람의 몫으로 남을 것 같습니다.

 

정리

  • 바이브 코딩은 AI에게 말로 설명해서 코드를 짜게 하는 방식입니다.
  • 2025년 2월에 처음 나온 말이고, 같은 해 콜린스 사전의 올해의 단어로 뽑혔습니다.
  • 코드를 몰라도 원하는 것을 만들 수 있지만, AI가 틀릴 수 있고 보안 허점도 생길 수 있습니다.
  • 간단한 일은 바이브 코딩만으로 충분하지만, 복잡한 프로그램은 아직 사람이 설계하고 확인해야 합니다.
  • 결국 무엇을 원하는지 정확히 말하고, 결과를 사람이 확인하는 것이 핵심입니다.

코딩을 몰라도 시작할 수 있다는 점은 분명히 큰 변화입니다. 다만 써 보니, AI가 코드를 대신 써 줄수록 결과를 알아보는 눈은 오히려 더 필요하다는 생각이 들었습니다. 모든 코딩이 바이브 코딩으로 바뀌는 날이 올지는 모르겠지만, 적어도 지금은 간단한 일부터 맡겨 보며 익숙해지는 것이 좋은 출발점인 것 같습니다.
