AI가 코드를 짜는 건 이제 익숙한 이야기입니다.
그런데 그 코드를 검토하고 "합쳐도 된다"고 승인하는 일까지 AI가 맡는다면 어떨까요?

[[ 이미지: 타이틀 (01-타이틀.png) ]]

앤트로픽이 2026년 11월 23일(미국 시간) 내놓은 '클로드 십(Claude Ship)'이 바로 그런 도구입니다.
뉴스만 보면 낯선 말이 많아서, 개발자가 아니어도 이해할 수 있게 순서대로 풀어 봤습니다.

 

◈ 한 줄로 말하면

  • 개발자가 올린 합치기 요청(PR)을 AI가 검토하고 고치며, 팀 규칙에 따라 승인 여부까지 판단하도록 돕는 도구입니다.
  • 어디까지 AI에게 맡길지는 각 팀이 규칙으로 정합니다.
  • 회사용 요금제 전용이고, 일부 기능은 아직 시험판(베타)입니다.

 

코드는 어떻게 합쳐질까?

여러 사람이 함께 만드는 프로그램은 원본 코드를 아무나 바로 고치지 않습니다.
각자 별도의 작업 줄기(브랜치)에서 고친 뒤, 원본 브랜치에 합쳐 달라고 요청합니다.

이 요청을 '풀 리퀘스트(PR)'라고 합니다.
깃허브 같은 코드 저장소 서비스에서 쓰는 말입니다.

[[ 이미지: 코드가 합쳐지기까지 (02-코드가-합쳐지기까지.png) ]]

 

◈ 코드 리뷰

다른 동료가 바뀐 부분을 읽고 실수나 위험한 곳이 없는지 봅니다.
글로 치면 다른 사람이 원고를 교정해 주는 단계입니다.

 

◈ 자동 검사

미리 만들어 둔 시험 프로그램이 바뀐 코드를 돌려 봅니다.
하나라도 실패하면 빨간 표시가 뜨고, 고칠 때까지 합치지 않는 팀이 많습니다.

 

◈ 승인과 병합

정해진 승인 담당자나 승인 규칙이 "합쳐도 된다"고 판단하면, 저장소의 병합 조건에 따라 원본에 합칩니다.
이것을 병합(머지)이라고 합니다.

 

왜 '검토'가 문제가 됐을까?

AI 코딩 도구가 퍼지면서 개발자가 만들어 내는 코드의 양이 늘어난 곳이 많습니다.
그런데 읽고 승인하는 일은 여전히 사람이 합니다.

그래서 합쳐 달라는 요청이 쌓이고, 검토가 병목이 됐다는 이야기가 해외 개발 업계에서 많이 나왔습니다.
클로드 십은 이 검토 단계를 겨냥한 도구입니다.

 

세 에이전트는 어디에 들어갈까?

클로드 십은 이름이 다른 에이전트 셋을 묶은 것입니다.
앞의 흐름에서 각자 맡는 칸이 다릅니다.

[[ 이미지: 세 에이전트의 자리 (03-세-에이전트의-자리.png) ]]

  • Code Review(코드 리뷰): 바뀐 코드를 읽고 문제를 중요한 것, 사소한 것, 원래 있던 것으로 나눠 알려 줍니다. 정식 출시됐습니다.
  • PR Steward(PR 관리): 자동 검사 실패, 다른 수정과의 충돌, 리뷰 의견을 보고 직접 고쳐 올립니다. 앤트로픽 문서에는 승인과 병합은 하지 않도록 설계했다고 적혀 있습니다. 베타입니다.
  • Claude Approvals(승인): 팀이 써 둔 규칙에 따라 승인 여부를 판단합니다. 규칙이 허락한 곳에서만 AI가 승인합니다. 베타입니다.

세 기능을 꼭 한꺼번에 쓸 필요는 없습니다.
앤트로픽 문서는 저장소 하나에서 코드 리뷰부터 켜고, 수정·승인 기능을 차례로 더하라고 권합니다.

개발자는 클로드 코드에서 '/ship' 명령을 실행해 변경 사항을 올리고 PR을 만든 뒤, 검토와 수정까지 진행할 수도 있습니다.
병합은 이 명령이 하지 않고, 개발자의 권한과 저장소 규칙에 따라 직접 합니다.

 

AI에게 승인을 맡겨도 될까?

가장 많이 나온 질문입니다.
앤트로픽은 어디까지 AI에게 맡길지를 팀이 정하게 해 두었습니다.

 

◈ 규칙 파일로 나눈다

저장소에 '.claude/approvals.yml'이라는 승인 규칙 파일을 둡니다.
바뀐 파일의 경로마다 사람 몇 명이 승인해야 하는지, AI가 의견만 낼지 승인까지 할지를 적습니다.

[[ 이미지: 승인 규칙 예시 (04-승인-규칙-예시.png) ]]

예를 들어 설명 문서의 오타 수정은 AI 승인으로 끝내고, 결제 코드는 사람 두 명이 보게 할 수 있습니다.
그림의 규칙은 이해를 돕기 위한 가상 예시입니다.

 

◈ '관찰 모드'로 먼저 본다

관찰 모드에서는 실제로 승인하지 않고, 규칙대로라면 어떻게 판단했을지만 보여 줍니다.
앤트로픽도 이 모드로 시작해 보라고 권합니다.

 

◈ 공식 문서에 적힌 주의

  • 발표 글, 제품 페이지, 문서 모두에 "AI를 쓰기 때문에 버그나 보안 취약점을 놓칠 수 있다"는 문구가 있습니다.
  • AI 승인을 허용하고 사람 승인을 요구하지 않는 규칙에 자동 병합까지 켜 두면, 사람이 최종 확인하지 않고 합쳐질 수 있습니다.
  • AI 승인 규칙을 만들었다고 코드 리뷰가 저절로 돌지는 않습니다. 리뷰를 따로 켜지 않으면 아무도 검토하지 않은 변경을 AI가 승인할 수 있어, 문서는 '코드 리뷰를 통과했을 때만 AI가 승인'하는 규칙을 예로 듭니다.

 

◈ AI 승인과 실제 병합은 다른 문제

깃허브는 '브랜치 보호 규칙'으로 승인 몇 개, 어떤 검사 통과를 병합 조건으로 정할 수 있습니다.
클로드 십의 승인 검사도 '필수 검사'로 지정해야 병합을 막습니다.

반대로 AI의 승인이 깃허브의 '승인 1개 필요' 조건을 채울 수는 있습니다.
그래서 문서는 깃허브에는 승인 1개까지만 요구하고, 사람 수는 규칙 파일에서 정하라고 안내합니다.

 

누가 쓸 수 있고, 비용은?

  • 조직에서 클로드 십을 켜려면 클로드 Team 또는 Enterprise 요금제와 깃허브 저장소가 필요합니다.
  • 데이터 무보관(Zero Data Retention), HIPAA 설정, 고객 관리형 암호화 키를 쓰는 조직은 이용할 수 없습니다.
  • 요금제와 별도로, 쓴 양(토큰)만큼 비용이 붙습니다. 관찰 모드에서도 규칙이 돌린 AI 판단과 코드 리뷰 비용은 청구됩니다.
  • 관리자는 기능별로 쓸 수 있는 금액 한도를 정할 수 있습니다.

조직용 클로드 십은 개인이 무료로 켜는 기능이 아닙니다.
개발자가 직접 실행하는 '/ship'은 일반 클로드 코드 사용량으로 계산됩니다.

회사에서 도입을 검토한다면 한도부터 정해 두는 것이 좋습니다.

 

기대와 걱정

앤트로픽은 자기 팀에서 6~9월 사이 합쳐진 PR이 두 배 넘게 늘고, 되돌린 비율은 40% 넘게 줄었다고 밝혔습니다.
다만 회사 안에서 잰 숫자이고, 코드 리뷰는 여러 확인 과정 중 하나라고 스스로 덧붙였습니다.

걱정도 있습니다.
AI가 작성한 코드를 다른 AI가 검토하면, 두 단계에서 비슷한 오류를 놓칠 가능성이 있다는 우려입니다.

쓴 만큼 내는 비용이 생각보다 커질 수 있다는 우려도 나왔다고 합니다.
무엇을 사람에게 남길지 정하는 일이 오히려 더 중요해진 셈입니다.

 

AI 개발 뉴스를 읽을 때 기억할 네 단어

  • 풀 리퀘스트(PR): "제가 고친 코드를 합쳐 주세요"라는 요청
  • 코드 리뷰: 동료가 바뀐 코드를 읽고 확인하는 일
  • 자동 검사: 시험 프로그램으로 코드를 돌려 보는 일
  • 병합(머지): 조건을 채운 코드를 원본에 합치는 일

이 네 단어를 알면 'AI가 코드 검토까지 맡는다'는 뉴스가 어느 단계 이야기인지 바로 보입니다.

클로드 십은 베타 기능이 포함돼 있어 내용과 조건이 바뀔 수 있습니다. 2026년 11월 23일 앤트로픽 발표 기준입니다.
